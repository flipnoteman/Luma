The Luma Guide

Migration

From 0.5.1 to 0.5.2

0.5.2 is a patch release that adds a great deal (complex arrays and FFTs, sparse matrices, dense linear algebra, image and filter operations, feature detection, interpolation and warps, accumulators, texture reads) and keeps the 0.5.1 API, with the few exceptions below. Most programs compile as they are. One behaviour changes without a compile error: matmul runs in TF32 on CUDA devices with tensor cores.

matmul is TF32 by default on CUDA

On a CUDA device of compute capability 8.0 or higher (Ampere and later) matmul rounds its operands to TF32 (10 bits of mantissa) and accumulates in f32, so results differ from the exact f32 product (each entry is within 1.5e-3 of the sum of the absolute values of its terms). Other backends and older devices compute f32 products as before. Where the exact product matters, call matmul_f32 for that product, or turn TF32 off for a context:

use luma::*;

let exact = Context::with_options(ContextOptions::default().tf32_matmul(false))?;  // or LUMA_TF32_MATMUL=0
assert!(!exact.tf32_matmul());
let a = Array::from_slice_on(&exact, &[1.0f32, 2.0, 3.0, 4.0], [2, 2])?;
let b = Array::from_slice_on(&exact, &[1.0f32, 0.0, 0.0, 1.0], [2, 2])?;
assert_eq!(a.matmul_f32(&b).to_vec()?, a.to_vec()?);   // the exact product of one call
assert_eq!(a.matmul(&b).to_vec()?, a.to_vec()?);       // the context's `matmul` is exact too
Ok::<(), luma::LumaError>(())

matmul_tf32 forces TF32 whatever the context says, and matmul_batched is always f32 (Tensor cores).

API changes that can break code built against 0.5.1

  • Reduction has a new variant, Product (the product of the elements, for reduce and reduce_axis). A match over Reduction without a wildcard needs an arm for it:

    use luma::*;

fn name(op: Reduction) -> &'static str {
    match op {
        Reduction::Sum => "sum",
        Reduction::Min => "min",
        Reduction::Max => "max",
        Reduction::SumOfSquares => "sum of squares",
        Reduction::Product => "product",              // new in 0.5.2
    }
}
assert_eq!(name(Reduction::Product), "product");

  • The re-exported BindingKind has two new variants, Sampler and Texture2d (the bindings of a sampler and a texture_2d<f32> in a kernel). An exhaustive match over luma::BindingKind needs arms for them, or a wildcard.

  • Array<f32>::clamp takes impl Operand<f32> bounds (an array, a reference to one, an f32 or a Scalar) where it took two f32. Calls with f32 values compile as before; a bound whose type used to be inferred from the f32 parameter (x.clamp(v.into(), 1.0)) must now be spelled out (x.clamp(f32::from(v), 1.0)).

For backend implementers

These matter only to code that implements or drives the HAL crates directly (luma-hal-core and the backend crates); users of Array are not affected. The new Backend methods all have default implementations.

  • Backend::compile_kernel and Backend::compile_naga take trust: luma_core::hal::KernelTrust (Checked, UncheckedBounds, Trusted) where they took trusted: bool: pass Trusted for true and Checked for false. UncheckedBounds is the kernel of unsafe KernelBuilder::unchecked_bounds.
  • DiskCache::load_pipelines returns Option<PipelineBlob>, the cache file as read; PipelineBlob::data() is the driver’s cache data to hand to the driver, so the file is no longer copied to cut its header off.
  • DeviceInfo has a new field, compute_units: Option<u32>: a struct literal needs it.
  • New variants: Expr::Texture in the kernel IR (TextureOp::Load, Gather, Sample), thirteen math functions in IrUnOp (see the enum) and CudaArgAbi::Texture / Unbound; an exhaustive match over any of them needs the new arms. A backend without textures leaves Backend::texture_caps at its default (None).
  • luma_wgpu::emit_with takes hardware_f32_atomics: bool; pass false for the compare-and-swap form of the f32 atomic add, true where the device has SHADER_FLOAT32_ATOMIC.
  • luma_cpu::WorkgroupPool::dispatch takes a &CostHint (the cost the pool has learned for the kernel, CostHint::default() for none), and CompiledCpuKernel, WorkgroupCtx and CpuMathTable have new public fields.

New in 0.5.2 that you may want

  • Fourier transforms, complex numbers, sparse matrices, dense linear algebra, images and filters, the vision chapters, interpolation, image transforms and filters (including the opt-in Interp::LinearHardware), incremental accumulation and compact integers (Array<u8>, i8, u16, i16).
  • matmul_nt, matmul_tn, matmul_tt and dot; prod / product and the *_by_key reductions; sort_by_key, set_unique, set_union and set_intersect; the elementwise functions of ArrayFire’s arith.h.
  • ContextOptions::tf32_matmul, Context::tf32_matmul(), matmul_f32, matmul_tf32 (Performance guide).
  • The plan cache of eager evaluation (LUMA_PLAN_CACHE), compile worker threads (LUMA_COMPILE_THREADS) and the CPU backend’s native matrix products (Performance guide).
  • A disk cache keyed by a hash of the sources that generate the code: the first run after the upgrade compiles every kernel again (FAQ).
  • KernelBuilder::unchecked_bounds (unsafe) for custom kernels (Custom kernels).

From 0.4 to 0.5

0.5 splits Luma into a workspace of six crates with one cargo feature per backend, adds native CUDA, Metal and CPU backends next to wgpu, and changes a few things that code written against 0.4 can trip over. Ordinary array code (Array, iterate, custom kernels) compiles as it is.

Software wgpu adapters are never used

Mesa llvmpipe, SwiftShader and WARP are refused by the wgpu backend: it never requests a fallback adapter and refuses DeviceKind::Cpu. A CPU device (LUMA_DEVICE=cpu, Context::cpu(), or Auto without a GPU) is now the native cpu backend, which every build includes. If your program ran on a software Vulkan adapter before, it now runs on the native CPU backend (or returns an error when LUMA_DEVICE=gpu is set) (Choosing a device).

LumaError carries strings, not wgpu types

Adapter, device and readback errors in LumaError hold backend-neutral strings instead of wgpu types, so a match that destructured a wgpu error now reads the message. luma::wgpu is re-exported only with the wgpu feature: code that used it needs that feature, or its own wgpu dependency. Features and the profiling types are re-exported from luma_core.

Crates and features

Luma is a workspace of six crates: luma-hal-core (the kernel IR and the backend interface), luma-hal-wgpu, luma-hal-metal, luma-hal-cuda and luma-hal-cpu (one backend each, with its own code generator), and the root luma crate. The features wgpu, metal and cuda each enable one GPU backend, and all are on by default; the CPU backend is always built. To build with one GPU backend only:

cargo build --no-default-features --features cuda
cargo build --no-default-features --features metal
cargo build --no-default-features --features wgpu

In Cargo.toml: luma = { version = "0.5", default-features = false, features = ["cuda"] }.

GraphLaunch takes a Dispatch

The graph interface of the backend trait, GraphLaunch, takes a Dispatch (direct or indirect) instead of workgroup counts. This matters only if you implement a backend; users of Array are not affected.

New in 0.5 that you may want

  • Choosing a backend: ContextOptions::backend, Context::{cuda, metal, wgpu, cpu, backend} and LUMA_BACKEND (Environment variables, FAQ). Auto tries CUDA, then Metal, then wgpu, then the native cpu backend. The CUDA backend needs only the NVIDIA driver, no CUDA toolkit. LUMA_CPU_THREADS sets the thread count of the cpu backend.
  • Context::device() returns a DeviceSummary { backend, name, software }, and Context::device_name() the name.
  • Array::permute_axes and swap_axes (lazy views, like transpose), with _mut forms (Views and writes).
  • Context::memory_stats() and Context::trim() (Performance guide).
  • iterate_until_all and compile_until_all loops replay a block of steps as one graph on backends that capture them (CUDA, Metal, CPU) (Loops).
  • compile_until_all and CompiledUntil: a loop of iterate_until_all traced once and run on many states (Loops). A time-blocked stencil also covers up to four f32 arrays of an eval loop evaluated together (Loops).

From 0.3 to 0.4

0.4 changes the type of comparisons: they return boolean arrays (Array<bool>) instead of Array<u32>. Most 0.3 code compiles as it is, because booleans promote to numbers the way they do in NumPy (below). Everything else in 0.4 is added (the list below).

Comparisons return Array<bool>

lt, le, gt, ge, eq, ne and is_finite / is_nan / is_inf return Array<bool>. On the GPU a bool is one bit (n booleans are ceil(n / 32) u32 words: a custom kernel that took a comparison as one u32 per element reads (a[i >> 5u] >> (i & 31u)) & 1u now); on the host from_slice, to_vec and item use plain bools.

What compiles unchanged:

  • select(&cond, a, b), sum_where(&cond) and Fields::select take an Array<bool>, and still take an Array<u32> (non-zero is true), so code that builds its own u32 conditions is as before.
  • bool * bool is the logical and: a.gt(0.0) * b.gt(0.0).
  • A boolean array times a number is the number where the boolean is true and 0 elsewhere, in either order and with a scalar: mask * &x, &x * mask, mask * 0.5. + and - convert the booleans to the 0 and 1 of the other operand’s type first. These work for f32, u32, i32, f64 and Df32 arrays, and the product fuses as a select, not a cast and a multiply.
  • sum() of booleans counts the true elements and returns an Array<u32> (as in NumPy), also count(), sum_axis and cumsum.

What does not:

// 0.3
let m: Array<u32> = x.gt(0.0);              // the type of a comparison was named
let both = &x.gt(0.0) + &y.gt(0.0);         // 0, 1 or 2
let idx = x.gt(0.0).cumsum(0) - 1u32;       // running count, minus one
let hit = x.gt(0.0);  let miss = &hit ^ 1u32;
// 0.4
let m: Array<bool> = x.gt(0.0);
let both = x.gt(0.0).to_u32() + y.gt(0.0).to_u32();    // or `|` / `&` for a logical result
let idx = x.gt(0.0).cumsum(0) - 1u32;                  // cumsum of booleans is a u32 array: unchanged
let miss = !&hit;

Also changed: a comparison is no longer an index (take, put: convert with to_u32()), has no /, % or shifts (convert first), and reads back as Vec<bool>. An integer literal next to a boolean array needs a suffix (mask * 2u32), since u32 and i32 arrays are both valid results.

use luma::*;

let x = Array::from_slice(&[1.5f32, -2.0, 3.0, -4.0], 4)?;
let above: Array<bool> = x.gt(0.0);
let both = &above & &x.lt(2.0);                    // booleans combine with & | ^ !
assert_eq!(above.count().item()?, 2);
assert_eq!(both.to_vec()?, vec![true, false, false, false]);
assert_eq!(above.to_f32().to_vec()?, vec![1.0, 0.0, 1.0, 0.0]);
assert!(above.any().item()?);
assert!(!above.all().item()?);
assert_eq!(select(&above, 1.0f32, 0.0).to_vec()?, vec![1.0, 0.0, 1.0, 0.0]);

// Promotion, as in NumPy: the number where true, 0 elsewhere.
assert_eq!((&above * &x).to_vec()?, vec![1.5, 0.0, 3.0, 0.0]);
assert_eq!((&above * 0.5).to_vec()?, vec![0.5, 0.0, 0.5, 0.0]);
assert_eq!((&x + &above).to_vec()?, vec![2.5, -2.0, 4.0, -4.0]);
// A `u32` condition still works.
let words = Array::from_slice(&[1u32, 0, 7, 0], 4)?;
assert_eq!(select(&words, &x, 0.0).to_vec()?, vec![1.5, 0.0, 3.0, 0.0]);
Ok::<(), luma::LumaError>(())

The numeric reductions (reduce_axis, scan, mean, norm) are not defined for bool: convert with to_u32() or to_f32(). A masked-out NaN or infinity in mask * &x gives 0, where a multiplication would give NaN.

New in 0.4 that you may want

  • i32 arrays, casts and bool (to_u32, to_i32, to_f32; count, any, all).
  • matmul, axis statistics (reduce_axis, mean_axis, var_axis, std_axis), accumulating scatters (put_add, bincount, histogram), sorting, group-by, unique and quantiles. Axis reductions no longer evaluate a pending operand first (What fuses).
  • Guide pages for Scalar, elementwise math, convolution and the tridiagonal solvers, which earlier releases already had.

From 0.2 to 0.3

0.3 changes two things your 0.2 code can trip over. Almost everything else in 0.3 is added; the few behaviour changes (a lazy reshape of a view, fusion decided by a cost model, a larger buffer pool) are listed under Changed in the changelog.

Reductions are lazy arrays

In 0.2, sum, min, max, mean, norm and reduce returned host values. In 0.3 they return a one-element Array that fuses with what follows, so &x / &x.sum() stays on the GPU. Read the value with item()? (and reduce results with to_array()?):

// 0.2
let total: f32 = x.sum()?;
// 0.3
let total: f32 = x.sum().item()?;

use luma::*;

let x = Array::from_slice(&[1.0f32, 2.0, 3.0, 4.0], 4)?;
assert_eq!(x.sum().item()?, 10.0);
assert_eq!(x.max().item()?, 4.0);

// Several reductions in one pass over the data come back as an array:
let both = x.reduce([Reduction::Min, Reduction::Max]);
assert_eq!(both.to_array::<2>()?, [1.0, 4.0]);

// Staying on the GPU:
let mean_removed = &x - &x.mean();
assert_eq!(mean_removed.to_vec()?, vec![-1.5, -0.5, 0.5, 1.5]);
Ok::<(), luma::LumaError>(())

The [f32; 2] and [f32; 4] reductions (vec2 / vec4 element arrays) still return host values.

Broadcasting per axis

An extent of 1 now broadcasts: [N, 1] + [1, M] is [N, M], also for the branches of select and in compound assignment. Code that relied on a shape mismatch being an error between such shapes now gets a result. broadcast_to(shape) makes it explicit.

New in 0.3 that you may want

  • Views that fuse into the reading kernel (slice, pad, flip, transpose, take, concat, …) and mutable views with assign.
  • Records (luma::fields!) for solver state.
  • Bit operations on u32, Df32 and f64.
  • iterate_until_all with a device-side stop rule.
  • Context::cost_model, Profile::splits, LUMA_CHECK_FINITE, and an on-disk cache of compiled pipelines (Environment variables).

The complete list, including performance changes and fixes, is in the changelog.
